# Инструкция для Cursor: production-ready сайт-портфолио

## Задача

Разработай полноценный production-ready персональный сайт-портфолио по требованиям из файла [`TECHNICAL_SPEC.md`](./TECHNICAL_SPEC.md).

Данные и материалы владельца сайта будут находиться в [`CONTENT_BRIEF.md`](./CONTENT_BRIEF.md). Не придумывай биографию, опыт, клиентов, отзывы, результаты проектов, контакты или юридические данные. Если поле не заполнено, используй явно обозначенный временный контент `TODO` и внеси его в список недостающих данных.

Итог должен быть не демонстрационным макетом и не набором статичных страниц, а готовым к публикации продуктом с рабочей административной панелью, формами, базой данных, SEO, аналитикой, безопасностью и инструкцией по развёртыванию.

## Важно: контент уже заполнен

`CONTENT_BRIEF.md` содержит реальные данные Содирхона Сидикова, тексты, контакты, достижения, услуги и шесть проектов. `content/portfolio-content.json` содержит те же сведения в структурированном виде для seed/import.

Не возвращай задачу пользователю с формулировкой «бриф пустой» и не останавливай разработку из-за пунктов в `OPEN_ITEMS.md`. Эти пункты нужны только перед финальной публикацией. Для полноценной v1 данных достаточно.

Если у проекта пока нет публичного скриншота:

- создай аккуратную типографическую обложку на основе реального названия, стека и схемы архитектуры;
- не изображай несуществующие экраны продукта как реальные;
- оставь возможность позже заменить обложку через админку;
- продолжай разработку остальных разделов.

Три главных кейса для главной страницы:

1. Production-система лояльности.
2. Карта монтажей с Bitrix24 и Яндекс.Картами.
3. Smile AI для Альфа Хакатона.

Фотографию владельца не использовать. Новый дизайн должен быть светлым, тёплым, минималистичным и editorial/product по характеру - без неона и без тёмно-синей основы.

## Роль

Работай как команда из:

- senior product designer;
- senior frontend-разработчика;
- backend-разработчика;
- motion-дизайнера;
- DevOps-инженера;
- QA-инженера.

Принимай разумные технические решения самостоятельно, но не изменяй продуктовые требования без фиксации причины.

## Источники требований

Используй документы в следующем порядке приоритета:

1. Прямые сообщения пользователя в Cursor.
2. Заполненные данные из `CONTENT_BRIEF.md`.
3. Требования из `TECHNICAL_SPEC.md`.
4. Этот файл.

При конфликте требований сообщи о конфликте и предложи наиболее безопасный вариант.

## Базовая архитектура

Рекомендуемый стек:

- Frontend: Next.js с App Router и TypeScript.
- UI: Tailwind CSS или CSS Modules, единая система дизайн-токенов.
- Анимации: Motion/Framer Motion и GSAP только там, где это оправдано.
- 3D: Three.js только для отдельного вау-элемента с graceful degradation.
- Backend API: FastAPI.
- База данных: PostgreSQL.
- Миграции: Alembic.
- Админка: защищённый интерфейс внутри проекта либо отдельный frontend-модуль.
- Медиа: S3-совместимое хранилище или Cloudflare R2.
- Email: транзакционный почтовый сервис через серверный API.
- Уведомления: Telegram Bot API.
- Локальная разработка: Docker Compose.
- Frontend production: Vercel или согласованный аналог.
- Backend production: Docker-контейнер на VPS или согласованной платформе.

Если репозиторий уже содержит другой согласованный стек, сначала проведи аудит и не переписывай рабочую архитектуру без необходимости.

## Обязательные правила реализации

1. Не выдумывай персональные данные и проекты.
2. Не вставляй секреты, токены и пароли в исходный код.
3. Добавь `.env.example` без реальных секретов.
4. Все входные данные валидируй на клиенте и сервере.
5. Административные маршруты и API должны требовать авторизацию.
6. Ограничь тип и размер загружаемых файлов.
7. Добавь rate limiting и защиту форм от спама.
8. Поддерживай клавиатурную навигацию и `prefers-reduced-motion`.
9. Тяжёлые анимации и 3D не должны блокировать контент.
10. Сайт должен оставаться функциональным при отключённом JavaScript настолько, насколько это возможно для выбранной архитектуры.
11. Не используй чужие изображения, шрифты или видео без понятной лицензии.
12. Парсеры не должны обходить авторизацию, CAPTCHA, ограничения доступа или правила площадок.

## Режим работы

### Этап 1. Аудит

Перед разработкой:

- изучи все файлы репозитория;
- прочитай `TECHNICAL_SPEC.md` и `CONTENT_BRIEF.md` полностью;
- проверь заполненность контента;
- составь список недостающих данных;
- зафиксируй принятые допущения;
- предложи структуру проекта и этапы реализации;
- проверь, нет ли уже существующих компонентов, настроек или пользовательских изменений, которые нужно сохранить.

Не удаляй существующий код или пользовательские изменения без явной необходимости.

### Этап 2. Основа проекта

- Настрой frontend и backend.
- Добавь Docker Compose для локальной базы данных и backend.
- Настрой переменные окружения.
- Создай модели данных и миграции.
- Реализуй базовую авторизацию администратора.
- Подготовь дизайн-токены, типографику и компоненты интерфейса.

### Этап 3. Публичная часть

Реализуй:

- главную страницу;
- страницу «Обо мне»;
- каталог проектов;
- страницы кейсов;
- услуги;
- контакты и рабочую форму;
- юридические страницы;
- страницу 404;
- адаптивные версии;
- анимации и переходы;
- SEO-метаданные и превью ссылок.

### Этап 4. Административная панель

Реализуй управление:

- главной страницей;
- профилем владельца;
- проектами и контентными блоками кейсов;
- категориями;
- услугами;
- отзывами и клиентами;
- контактами;
- файлами и резюме;
- SEO-полями;
- входящими заявками;
- статусами `draft`, `published` и `archived`.

### Этап 5. Интеграции

- Отправка заявки на email.
- Уведомление о заявке в Telegram, если переданы данные бота.
- Подключение выбранной аналитики.
- Подключение объектного хранилища.
- Настройка production-конфигурации.

### Этап 6. Проверка

Обязательно выполни:

- typecheck;
- lint;
- unit-тесты критической логики;
- интеграционный тест API формы;
- smoke-тест основных страниц;
- проверку адаптивности;
- проверку навигации с клавиатуры;
- проверку `prefers-reduced-motion`;
- проверку пустых и ошибочных состояний;
- production build frontend и backend;
- проверку миграций на чистой базе.

Не заявляй, что функция работает, если она не проверена.

## Переменные окружения

Создай `.env.example` как минимум со следующими группами переменных:

```dotenv
# Frontend
NEXT_PUBLIC_SITE_URL=
NEXT_PUBLIC_API_URL=
NEXT_PUBLIC_ANALYTICS_ID=

# Backend
APP_ENV=development
APP_SECRET=
DATABASE_URL=
ALLOWED_ORIGINS=
ADMIN_EMAIL=
ADMIN_INITIAL_PASSWORD=

# Storage
S3_ENDPOINT=
S3_REGION=
S3_BUCKET=
S3_ACCESS_KEY_ID=
S3_SECRET_ACCESS_KEY=
S3_PUBLIC_URL=

# Email
EMAIL_PROVIDER_API_KEY=
CONTACT_RECIPIENT_EMAIL=
EMAIL_FROM=

# Telegram
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=

# Anti-spam
TURNSTILE_SITE_KEY=
TURNSTILE_SECRET_KEY=
```

Названия можно адаптировать к выбранным библиотекам, но все используемые переменные должны быть документированы.

## Работа с незаполненным контентом

Если данных пока нет:

- сохраняй полноценную структуру страницы;
- используй нейтральные заглушки с меткой `TODO`;
- не создавай фальшивые отзывы, компании, цифры или награды;
- не публикуй незаполненные проекты;
- собери все пробелы в `MISSING_CONTENT.md`;
- добавь инструкции, где заменить каждое значение через админку.

## Парсеры

Интеграции с Kwork и другими площадками относятся к отдельному этапу после запуска основной версии.

До реализации нужно зафиксировать:

- разрешённый источник данных;
- наличие официального API;
- цель обработки;
- частоту запросов;
- правила хранения данных;
- ограничения площадки;
- публичность результата.

По умолчанию функциональность парсеров должна быть доступна только администратору и не должна блокировать запуск портфолио.

- инструкцию по наполнению сайта;

## Definition of Done

Работа считается завершённой только если:

- все must-have функции согласованной версии реализованы;
- frontend и backend собираются без ошибок;
- миграции применяются на чистой базе;
- административная панель защищена;
- данные редактируются без изменения исходного кода;
- форма сохраняет заявку и отправляет настроенные уведомления;
- нет критических ошибок на мобильных и настольных устройствах;
- реализованы SEO, доступность и обработка ошибок;
- секреты отсутствуют в репозитории;
- инструкции позволяют развернуть проект с нуля;
- все непроверенные или незавершённые пункты явно перечислены.
